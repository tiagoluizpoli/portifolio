# Example: Emergency Rollback — Recovery from a Bad Commit

**Scenario**: A commit introduced a regression that breaks the login flow in production. The commit is already on the shared `main` branch. We need to recover fast without losing other people's work.

---

## Triage: Understand the Situation First

```bash
# What's the current state?
$ git log --oneline -8
9a8b7c6 feat(analytics): add page view tracking
8z7y6x5 fix(auth): refactor session initialization   ← PROBLEM COMMIT
7w6v5u4 feat(notifications): add real-time updates
6v5u4t3 test(auth): add session persistence E2E tests
5u4t3s2 feat(auth): add team-based role on signup
...

# What exactly did the problem commit change?
$ git show 8z7y6x5 --stat
$ git show 8z7y6x5
```

Reading the diff reveals: the session initialization was reordered — the cookie is now set AFTER the redirect, so the session is never available on the first page load.

---

## Option A: Revert (Safest — Preserves History)

A revert creates a new commit that undoes the changes. The original commit remains in history. This is always the right choice on a shared branch.

```bash
# Create a revert commit
$ git revert 8z7y6x5
# Editor opens with pre-filled message — review and save

# Revert commit message (auto-generated by git, then edited):
# revert: fix(auth): refactor session initialization
#
# This reverts commit 8z7y6x5.
#
# The session initialization reorder caused the cookie to be set after
# the redirect response, making the session unavailable on the target
# page's first load. Rolling back while a correct fix is designed.
#
# Tracked in: #312

$ git log --oneline -5
b9c0d1e revert: fix(auth): refactor session initialization
9a8b7c6 feat(analytics): add page view tracking
8z7y6x5 fix(auth): refactor session initialization   ← still in history
7w6v5u4 feat(notifications): add real-time updates
6v5u4t3 test(auth): add session persistence E2E tests

# Verify revert works
$ pnpm guard
✓ All checks pass
```

## Option B: Using `git reflog` to Recover Lost Work

**Scenario**: You accidentally ran `git reset --hard HEAD~3` and lost 3 commits that haven't been pushed yet.

```bash
$ git reflog | head -20
9a8b7c6 HEAD@{0}: reset: moving to HEAD~3    ← the accident
b1c2d3e HEAD@{1}: commit: test(auth): ...
a0b1c2d HEAD@{2}: commit: feat(notifications): ...
f9e0d1c HEAD@{3}: commit: fix(auth): ...
...

# The lost commits still exist — reflog tracks every HEAD movement
# Recover by creating a branch at the pre-reset commit

$ git branch recovery/lost-commits b1c2d3e
$ git checkout recovery/lost-commits
$ git log --oneline -5
b1c2d3e test(auth): add session persistence E2E tests     ← recovered ✅
a0b1c2d feat(notifications): add real-time updates        ← recovered ✅
f9e0d1c fix(auth): refactor session initialization        ← recovered ✅
...
```

## Option C: Cherry-Pick (If Only Some Commits Are Good)

**Scenario**: A series of 4 commits was pushed to `main`, but only commits 1, 2, and 4 are good. Commit 3 has a bug. Need to build a clean branch without commit 3.

```bash
$ git log --oneline -5
4d3c2b1 test(auth): add E2E test for session expiry   ← good
3e4f5g6 feat(auth): add session expiry handling       ← BAD (bug here)
2b3c4d5 feat(auth): add magic link login              ← good
1a2b3c4 feat(auth): add GitHub OAuth provider         ← good
0z9y8x7 chore(deps): update dependencies             ← good

# Create a clean branch without commit 3
$ git checkout -b fix/clean-auth-without-bad-commit 0z9y8x7

# Cherry-pick the good commits
$ git cherry-pick 1a2b3c4   # GitHub OAuth
$ git cherry-pick 2b3c4d5   # Magic link
# Skip 3e4f5g6 entirely — fix the bug here instead
# (implement the correct session expiry handling)
$ git cherry-pick 4d3c2b1   # E2E tests (may need adjustment)

# Create a correct fix commit in place of the bad one:
$ git commit -m "feat(auth): implement session expiry with correct cookie lifecycle"

$ git log --oneline -5
# Clean history without the bad commit
```

## Reflog Time Machine

`git reflog` is your time machine. Git keeps a record of every position HEAD has been in for the last 90 days (default). Nothing you've committed is truly lost until the reflog expires.

```bash
$ git reflog | head -20
HEAD@{0}: current position
HEAD@{1}: previous position
HEAD@{2}: ...

# Common recovery operations:
$ git checkout HEAD@{5}               # Inspect state from 5 moves ago
$ git branch recovery/name HEAD@{5}   # Create branch from any reflog position
$ git reset --hard HEAD@{3}           # Reset to 3 moves ago (destructive — careful)
```

## Decision Tree for Rollback Scenarios

```
Something is broken — how do I fix it?
│
├── The bad commit is on a SHARED branch
│   └── Use: git revert <commit>   → safe, always preserves history
│
├── The bad commit is LOCAL ONLY
│   ├── Most recent commit:
│   │   └── git commit --amend    → replace the commit entirely
│   │
│   └── Earlier commit:
│       └── git rebase -i HEAD~N  → edit/drop the bad commit
│
├── I ran git reset --hard and lost commits
│   └── git reflog                → find the lost HEAD position
│   └── git branch recovery/name HEAD@{N}
│
└── I staged the wrong files
    └── git restore --staged .    → unstage everything (changes preserved)
    └── git reset HEAD            → same as above
```

## Prevention > Recovery

The best rollback is the one you never need:

1. **Always stash before starting** — your escape hatch
2. **Always run guard before committing** — catch failures before they're in history
3. **One logical change per commit** — if a commit is bad, revert is surgical
4. **Never `--force` on shared branches** — if you have to ask if it's okay, it's not
5. **Run tests after cherry-picks** — cherry-pick doesn't guarantee tests pass in the new context
